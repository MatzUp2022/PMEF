# RFC-0010: Review Comment and Issue Reference

| Field | Value |
|---|---|
| **Status** | `DRAFT` — implemented 2026-11-27; awaiting RFC issue, WG review and TSC sign-off |
| **Target version** | 0.10.0 (two new optional properties; no breaking change) |
| **Depends on** | [RFC-0001](0001-provenance-asbuilt.md) (`review` block; open question 2) |
| **Working groups** | WG-Piping, WG-Steel, WG-Equipment |
| **Date** | 2026-11-27 |

## Abstract

The RFC-0001 `review` block records *who* checked an object and *what* the outcome was, but not
*why*. This RFC adds two optional properties to `review`: `comment` (the reviewer's note) and
`issueRef` (an absolute URI of the issue that documents the finding, typically a BCF topic).

## Motivation

- **UC-1 Rejections must be explainable.** A rejected recognition result ("false positive: cable
  bracket, not a pipe support") is training and audit data for the recogniser; without a reason
  the rejection cannot be evaluated.
- **UC-2 Corrections need context.** `reviewed` means "corrected, not yet accepted"; the next
  reviewer needs to know what was corrected and what is still open.
- **UC-3 Link to coordination.** Model-based coordination raises findings as BCF topics (BCF 3.0)
  or as issues in a document/workflow system. The object must point to that issue so that a
  viewer can open it from the object and vice versa.

## Detailed Design

`pmef-base.schema.json` `$defs/ReviewStatus` gains:

| Field | Required | Type | Description |
|-------|----------|------|-------------|
| `comment` | SHOULD if `status` is `rejected` | string, 1–2000 characters | Reviewer's note |
| `issueRef` | MAY | absolute URI | Issue that documents the finding |

Rules:

1. Both properties are allowed with every `status`, including `detected` (e.g. a note from an
   automatic plausibility check).
2. `comment` is plain text. It records the reason of *this* review, not a discussion thread;
   discussions live in the issue that `issueRef` points to.
3. `issueRef` **MUST** be an absolute URI without whitespace (schema `format: uri` plus a
   pattern, because format assertion is optional in Draft 2020-12). For BCF the value
   **SHOULD** be the BCF API URL of the topic
   (`…/bcf/3.0/projects/{project_id}/topics/{topic_guid}`); for a topic without a server,
   `urn:uuid:{topic_guid}`.
4. PMEF stores only the link. Issues, their status and workflow are not PMEF data
   (ecosystem: document management and workflows belong to ProDocAimAi, docs/ECOSYSTEM.md).
5. One `issueRef` per review. Several findings on one object are one issue with several
   comments in the issue system, not several references in PMEF.

The normative text is spec 02 §2.9.2.

## Backwards Compatibility

None. Every existing file stays valid. Like every other 0.10.0 addition, a file that uses the
new properties is invalid against the 0.9 schemas (`additionalProperties: false`).

## Alternatives Considered

- **Array of issue references** — rejected: one finding per review is the common case, and an
  issue system already groups related findings; an array can be added later without a break by
  a new property.
- **Embedding BCF markup (viewpoint, snapshot) in PMEF** — rejected: duplicates BCF and turns
  PMEF into a coordination format.
- **A separate `pmef:ReviewComment` object** — rejected: needs an `@id` and a relationship for a
  single string; the review block is already per object.

## Reference Implementation

- Schema: `pmef-base` `$defs/ReviewStatus` (`comment`, `issueRef`).
- Rust: `pmef_core::provenance::ReviewStatus` (`comment`, `issue_ref`); round trip in
  `pmef-core/tests/provenance_roundtrip.rs`.
- Validation: negative cases (empty or too long comment, relative or blank-containing
  `issueRef`) in `pmef-validate/tests/provenance.rs`.
- Example: `examples/asbuilt-recognition.ndjson` (generated by
  `scripts/generate-asbuilt-example.py`): `CW-301-PIPE-002` (`reviewed`, comment and BCF topic)
  and `CW-301-PS-901` (`rejected`, comment).
